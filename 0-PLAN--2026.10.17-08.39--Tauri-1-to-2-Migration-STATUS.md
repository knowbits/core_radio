## How to use this file (instructions for the implementing AI/LLM)

**Below `RESUME HERE` this is an append-only log of _completed_ work. Do not pre-populate it with
the plan's steps.**

- The plan file is the source of truth for *what to do*. This file records *what is done*.
- When — and only when — a step is **finished and verified**, append one entry at the bottom.
- Never add an entry for a step that is planned, in progress, or unverified. If something is
  partially done, keep working; do not log it. Record a blocker only as a labelled `BLOCKED` entry.
- **Why append-only / completed-only:** the plan changes while it is implemented. A file mirroring
  every planned step drifts whenever the plan is reordered, forcing constant maintenance. Recording
  only finished work means this file never needs reconciling against plan edits.
- Keep entries terse. The plan holds the detail; this holds the proof.
- **Update `RESUME HERE` in the same edit** as appending an entry. A stale resume block is worse
  than none — it sends the next session to the wrong place.
- **Log every verified step with one command** — it appends the entry and rewrites `RESUME HERE`
  together, lint-gated:
  `ai-plan-msg checkpoint --status <STATUS-file> --step <Letter.n> --title <t> --evidence <type>
  --changed <c> --verified <v> [--notes <n>] --next-step <s> --next-model "<tier>, <effort>"
  --phase <Letter|DONE>` (inside `ai-plan-runner.sh`, `--status` may be omitted). Modes and exit
  codes: [`AI--Plan-Runner.md`](./AI--Plan-Runner.md)'s "Protocol verbs (standalone)".
- **Fallback, only when `ai-plan-msg` is unavailable:** `ai-patch <STATUS-file>:"## Completed steps
  log" --append --replacement-file <entry-file>` and `ai-patch <STATUS-file>:"## RESUME HERE"
  --replacement-file <block-file>` — never `Edit` with old text. End the RESUME HERE block file with
  a blank line, `---`, blank line (the replace spans up to the next heading), and raise
  `AI_TOOLS_PATCH_MAX_GROWTH_FLOOR` for an entry over ~30 lines.

### Entry format

Append newest entries at the **bottom**:

```
### <ISO date> — Step <Letter.n>: <short step title>
- Evidence: <diff+check | investigation | config-validation | research-artifact | no-code>
- Changed: <files / modules touched, one line>
- Verified: <exact command(s) run> → <outcome, e.g. "12 passed", "lint: all checks passed">
- Notes: <anything non-obvious; deviations from the plan and why; follow-ups>
```

**A no-code step (analysis, diagnosis, research, an investigation that concludes no change is
needed) is a legitimate completed step, not a lesser one — hold it to the same concreteness, not an
easier bar.** `Changed:` may read `none (investigation only)` when genuinely nothing was edited —
that is not a gap to paper over. `Verified:` must still name something concrete: a command actually
run and its real output (e.g. a regression suite reused as a check), or, when no command applies,
the exact evidence the conclusion rests on — a file:line citation, a quoted command's output, a
specific tool result — never a bare unverifiable claim like "confirmed" or "looks correct" with
nothing behind it. Preserve exact references (file:line, command + outcome, doc section) a later
session would need to act on the finding without redoing the investigation.

**`Evidence:` names which of five kinds of proof this step rests on — pick exactly one, honestly,
not whichever sounds strongest:**

- `diff+check` — one or more real files changed, verified by a command that actually exercises the
  change (tests, build, a targeted script run against the new behavior).
- `investigation` — no functional/config change; a bounded read-only analysis whose conclusion is
  backed by file:line citations or quoted command output (e.g. "already adequate, confirmed by
  reading X in full" — a real audit, not a guess).
- `config-validation` — a configuration/schema/registration value changed, verified by a real
  validation command (linter, `--dry-run`, schema/lint check) rather than a test suite.
- `research-artifact` — an external fact (vendor docs, API/CLI behavior, a library version) was the
  load-bearing evidence; the exact source and the specific confirmed fact are named, not assumed.
- `no-code` — genuinely nothing was edited (`Changed: none` or `none (investigation only)`); the
  step's value is the recorded decision or conclusion itself.

**This declaration is load-bearing, not decorative: `ai-plan-lint.sh` requires it on every completed
entry, and `ai-plan-runner.sh` only treats a RESUME-HERE-changed iteration that touched no other repo
files (`suspicious_progress`) as real progress when the newest entry's `Evidence:` is honestly
`no-code` — any other declared type making that same claim is status-only churn masquerading as
progress, and does not reset the no-progress counter.** See
[`AI--Plan-Workflow-and-Status-Tracking.md`](./AI--Plan-Workflow-and-Status-Tracking.md) §3b.

For a blocker (rare — only when work cannot proceed), or an earlier step deliberately deferred to a
later session (it lets later steps checkpoint):

```
### <ISO date> — BLOCKED — Step <Letter.n>: <what is blocked>
- Reason: <precise blocker>
- Needs: <decision / input required to unblock>
```
